# 成本效率法则

## 核心原则（唯一且不可拆分）

**在保证太一系统整体正常运行的前提下，尽最大努力减少对大模型 token 的消耗。**

这条原则是一个整体，不可割裂解读：
- 保证系统运行 → **第一优先**，不可因省 token 导致系统功能降级或故障
- 减少 token 消耗 → **在此约束下的优化目标**，不可为省 token 牺牲交付质量

## 三级执行策略

### Tier 1 — 本地执行（零 token 消耗）
所有不依赖 LLM 推理的操作，优先本地执行：
- 系统命令（exec / bash / python）
- 文件读写、搜索、组织
- 定时任务调度、健康检查
- 网络请求（curl / web_fetch）
- Git 操作、文件转换
- 数据采集、日志分析
- 所有脚本化、规则化的操作

### Tier 2 — 低成本模型（低 token 消耗）
当需要 LLM 推理但任务简单时，优先使用低成本模型：
- 简单分类、关键词提取
- 格式化输出、模板填充
- 规则匹配、结构转换
- 默认选择 deepseek-v4-flash

### Tier 3 — 主力模型（必要才用）
仅在以下场景使用主力/高质量模型：
- 复杂推理、跨文档分析
- 生成式内容（日报、开发信、社媒文案）
- 情报分析、总结提炼
- 用户明确要求高质量输出的任务

## 执行规则

1. **本地方案 > LLM**：任何任务优先尝试纯脚本/规则方案，纯本地方案不可靠时切换到 LLM
2. **低成本 > 高成本**：必须用 LLM 时，deepseek-v4-flash 优先于更贵的模型
3. **批量 > 串行**：多条 LLM 调用合并为一次批量请求
4. **缓存 > 重复**：相同输入的结果缓存复用，避免重复消耗
5. **每次调用前自问**：这个 LLM 调用真的必要？可以用本地脚本替代吗？可以用低成本模型吗？

## 运营保障（最高优先级）

⚠️ 以下情况立即启用主力模型，不得因省 token 而犹豫：
- 用户明确要求高质量输出
- 本地方案/低成本方案已证明不可靠
- 系统故障诊断需要完整推理能力
- 定时任务（日报/开发信/报告）的生成质量不达标

## 违例处理

- 违反本法则（无谓消耗 token）→ 记录到 .learnings/ERRORS.md
- 因省 token 导致运营故障 → 触发 SRE 自检并优化判断逻辑
