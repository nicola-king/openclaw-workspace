# Karpathy 编程原则 (LLM 编码规范)

> **来源**: Andrej Karpathy / forrestchang/andrej-karpathy-skills
> **融合时间**: 2026-05-04 | **蒸馏更新**: 2026-05-18
> **定位**: Tier 2 上下文激活 (代码/开发任务时加载)
> **核心**: 减少 LLM 编码常见错误，提升代码质量

---

## 🎯 核心原则

### ① 负熵原则 — 编码前思考 (Think Before Coding) **（认知层）**

**不要假设。不要隐藏困惑。暴露权衡。**

执行前：
- 明确陈述你的假设。如果不确定，**追问**。
- 如果存在多种解读，**呈现它们** — 不要默默选择。
- 如果存在更简单的方案，**说出来**。必要时**反驳**。
- 如果不清楚，**停止**。指出困惑之处。**追问**。

**太一融合**: 与追问协议 (ASK-PROTOCOL.md) 对齐 — 模糊时追问，不盲目执行。

---

### ② 简洁优先 (Simplicity First) **（输出层）**

**解决问题所需的最少代码。不做推测。**

- 不添加超出要求的功能。
- 不为一次性代码做抽象。
- 不添加未被要求的"灵活性"或"可配置性"。
- 不为不可能的场景做错误处理。
- 如果写了 200 行但可以是 50 行，**重写**。

**自检**: "资深工程师会说这过度复杂吗？" 如果是，**简化**。

**太一融合**: 与负熵法则对齐 — 删除一切不必要的，极简黑客风。

---

### ③ 精准修改 (Surgical Changes) **（操作层）**

**只碰必须碰的。只清理自己造成的混乱。**

编辑现有代码时：
- 不要"改进"相邻代码、注释或格式。
- 不要重构没坏的东西。
- **匹配现有风格**，即使你会用不同方式。
- 如果注意到无关的死代码，**提及它** — 不要删除它。

当你的修改产生孤儿代码时：
- 删除**你的修改**导致未使用的 import/变量/函数。
- 不要删除预先存在的死代码，除非被要求。

**测试标准**: 每一行修改都应直接追溯到用户的请求。

**太一融合**: 与工具克制原则对齐 — 只做必要的事，最小权限。

---

### ④ 目标驱动执行 (Goal-Driven Execution) **（质量层）**

**定义成功标准。循环直到验证。**

将任务转化为可验证的目标：
- "添加验证" → "为无效输入写测试，然后让它们通过"
- "修复 bug" → "写一个复现它的测试，然后让它通过"
- "重构 X" → "确保测试在重构前后都通过"

多步骤任务时，陈述简要计划：
```
1. [步骤] → 验证: [检查]
2. [步骤] → 验证: [检查]
3. [步骤] → 验证: [检查]
```

**强成功标准**让你独立循环。**弱标准** ("让它工作") 需要不断澄清。

**太一融合**: 与验证优先法则 (VERIFICATION-FIRST.md) 对齐 — 验证 > 输出。

## 🔄 与现有宪法的融合

| Karpathy 原则 | 对应宪法 | 关系 |
|--------------|---------|------|
| 编码前思考 | 追问协议 | 强化追问，不盲目执行 |
| 简洁优先 | 负熵法则 | 删除冗余，极简输出 |
| 手术式修改 | 工具克制原则 | 最小权限，只做必要 |
| 目标驱动执行 | 验证优先法则 | 验证 > 输出，真实 > 完整 |

---

## ⚖️ 权衡说明

**这些原则偏向谨慎而非速度。** 对于琐碎任务，使用判断。

**何时放宽**:
- 紧急修复 (先执行，后验证)
- 概念验证 (快速原型)
- 已知模式 (标准实现)

**何时严格**:
- 生产代码
- 他人代码修改
- 复杂重构

---

## ✅ 自检清单 (编码前)

```
□ 我是否理解了需求？不确定的地方是否已追问？
□ 是否存在更简单的方案？我是否提及了？
□ 我的修改是否只触及必要部分？
□ 是否删除了我造成的孤儿代码？
□ 是否定义了可验证的成功标准？
□ 每一行修改是否都能追溯到用户请求？
```

**全部 ✅ → 开始编码**
**任一 ❌ → 停止，修正**

---

## 🎯 效果指标

这些原则生效的标志：
- diff 中不必要修改更少
- 因过度复杂导致的重写更少
- 澄清问题出现在实现前，而非错误后
