# 知识沉淀原则

> **来源**: Karpathy llm-wiki 蒸馏 | **融合时间**: 2026-05-18
> **定位**: Tier 1 常驻激活
> **核心**: 一次推导，反复使用

---

## 核心原则

**确认过的知识、配置、决策 → 写入持久化文档，不重复推导。**

同一概念不需要第二次推导，查到就直接用。每次推导都是 token 消耗，每次查阅都是 token 节省。

## 四层沉淀路径

### 第一层：代码层约定 → CLAUDE.md / 项目文档
- 架构决策（为什么选这个方案）
- API 用法（关键参数、边界条件）
- CI/CD 流程（部署步骤、环境变量）
- 配置文件格式（配置文件怎么写）
→ 写入项目根目录的 CLAUDE.md 或 docs/ 目录

### 第二层：工具配置 → TOOLS.md
- 工具特定参数（camera names, SSH hosts）
- 环境变量（API keys, 代理设置）
- 设备信息（型号、IP、端口）
→ 写入 workspace/TOOLS.md

### 第三层：跨会话上下文 → Memory 系统
- 用户偏好（语言、风格、格式要求）
- 关键引用（重要链接、参考文档）
- 项目状态（哪些已做、哪些待做）
- 决策记录（为什么这么选）
→ 写入 memory/core.md → memory/YYYY-MM-DD.md

### 第四层：全局知识 → wiki / constitution
- 技术原理（经过验证的）
- 最佳实践（复盘得出的）
- 系统架构（组件关系图）
→ 写入 wiki/ 或 constitution/

## 执行规则

1. **发现即沉淀**：任何经过验证的知识，第一时间写入对应层级
2. **先查再用**：处理任务前，先查是否已有沉淀知识
3. **不二次推导**：已有记录的知识直接复用，不重新推理
4. **索引化**：重要知识点建立关键词索引，便于检索
5. **轻量更新**：修改在原文上增量编辑，不重写全文

## 自检

```
□ 这个知识点之前是否遇到过？查过 Memory 了吗？
□ 这个配置/决策是否需要记录供以后使用？
□ 应该写在哪个层级？（代码/工具/会话/全局）
□ 同一知识点是否写到了多个地方？（需要去重合并）
```

## 违例示例

```
❌ 每次都用 model 重新推导 API 参数
❌ 重复搜索同一个技术问题
❌ 同样格式的日报每次从零设计
❌ 用户偏好的记录只靠对话记忆
```
